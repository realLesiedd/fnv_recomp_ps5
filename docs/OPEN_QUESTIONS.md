# Open questions

Questions this repository does not answer. Each one cites the note or the code that raises it. Plans that already have a done criterion live in [STATUS.md](../STATUS.md#future-plans). This file is the unknowns those plans depend on, and the risks that are not yet a plan.

A line marked **speculation** is a guess. The tree does not show it.

## Toolchain

- **Which PS5 firmware the app actually requires.** The player page says the build was tested on firmware 13.42 ([README.md](../README.md)). `ps5/build.sh` signs with `--module-sdk 0x02000009` and `--companion-sdk 0x08050001` and links a specific tree: Nazky's ps5-plume-triangle, its PacBrew sysroot at `v0.40.2`, PS5_Mesa's `libvulkan_radeon.ps5.a`, and DXVK 2.7.1. Nothing records what happens on a firmware other than 13.42, or on a newer payload SDK.
- **How much of the PS5 stack is pinned by accident.** The DXVK patch (`ps5/dxvk/dxvk-ps5.patch`) is a diff against 2.7.1. `ps5/README.md` says to clone that tag and apply the patch. A later DXVK does not apply it as-is. Whether a later tag is worth the rebase is the long-term maintenance item in the status file. The reason to stay is "the patch matches this tag", not a measured bug in later releases.
- **The generated C is not reviewable from this repository.** `tools/recomp.py` writes `gen/` from the player's own `FalloutNV.exe`, and `.gitignore` excludes `gen/`. Function counts, the unsupported-instruction count, and the import list exist only after that run. The last count written down anywhere in the tree is in the commit that added the roadmap: unsupported sites fell from 132 to 119, and that commit calls the remainder data bytes the disassembler treated as code. The "209" figure in the first status bullet is older than the MMX and x87 work.
- **fnv_decomp is a build input with no licence for its contents.** [docs/BUILDING.md](BUILDING.md) and [CREDITS.md](../CREDITS.md) say the recompiler reads `build/units.json` (68,657 function addresses) and `build/image_check.json` from a local checkout, and that nothing from that project is copied into this repository. What a redistributor may ship, given that the addresses came from that checkout, is a legal question this tree states and does not answer. See [Legal and assets](#legal-and-assets).

## Recompiler and guest CPU

- **Which rejected mnemonics still occur in real code.** `tools/recomp.py` raises `Unsupported` for `pcmpgtb`, MMX beyond `movq` / `paddw` / `psubw` / `pcmpgtw` / bitwise, unknown x87 and SSE, a `gs` segment override, nested `enter`, `hlt`, and a string opcode that `string()` does not recognise. A hit becomes `rt_unimpl`, and `rt_unimpl` in `rt/main.c` stops the process. The last recorded claim is that the remaining sites are data, not code. The addresses are not checked in. A future disassembly pass could disagree.
- **x87 is a `double` stack.** `rt/x86.h` keeps `st[8]` as `double`. 80-bit loads and stores go through `ld80` / `st80`. The status notes do not attribute any physics or camera bug to that rounding. **Speculation:** Havok, or any long reduction the original x87 did in 80-bit registers, could diverge. Nothing here shows a divergence.
- **Flags and `mxcsr` are partial.** `eflags` is documented as meaningful across `pushfd` / `popfd` and at function boundaries, with conditions computed lazily from the last flag writer. `mxcsr` is stored and loaded (`ldmxcsr` / `stmxcsr` in the recompiler). The header does not describe trap-on-denormal, rounding-mode changes taking effect for SSE arithmetic, or floating-point exceptions. No play note reports a bug from this.
- **Guest writes to code bytes do not change the code that runs.** Indirect calls go through the table in `rt/main.c` (`rt_call_ind`) to the C function emitted for that address. The bytes mapped from the executable at `map_image` are the data the game reads. A store into `.text` would change those bytes and would not change `f_ADDR`. **Speculation:** the game patches its own code at runtime. This repository does not show that. The deliberate patches are the five `HOOKS` in `tools/recomp.py`.
- **`SuspendThread` is ignored.** `k_SuspendThread` in `rt/kernel32.c` logs and returns 0. No status note says the game called it. If a path depends on a thread actually stopping, it will not.
- **SEH and C++ `throw` stop the process.** Covered as a mid-term plan. The open part is whether any quest, add-on, or script on the 1.4.0.525 path actually throws. The played route in the status notes never logged the fatal message. **Speculation:** a mod or xNVSE will be the first thing that throws.

## Rendering

- **The shipping path is DXVK on Vulkan.** `rt/hostd3d9.cpp` replays the front end onto DXVK's `IDirect3DDevice9`. On PS5 the patch's WSI creates a `VK_KHR_display` plane surface and prefers a 3840x2160 mode (`ps5/dxvk/dxvk-ps5.patch`). `ps5/glprobe/` is a separate OpenGL ES probe, built by its own Makefile, and it is not linked into the app. It is not a second renderer for the game.
- **Which display modes RADV enumerates on a real TV.** The WSI logs `PS5 WSI: TV mode WxH @ N Hz` and, if a 3840x2160 mode exists, picks the first one it finds. It does not rank modes by refresh. Whether a 120 Hz mode is in that list at 4K, or only at a lower resolution, is not recorded. The long-term 120 fps goal depends on the answer, and on the engine limit below.
- **Occlusion and timestamp queries return constants.** `q_GetData` in `rt/d3d9.c` reports an event query as done, an occlusion query as 100000 pixels, and timestamps from the frame counter. `q_Issue` does nothing. The open question is whether the game calls them on the path that draws the Mojave. A missing-import log will not say so: the methods are on the vtable. **Speculation:** a constant "visible" result would only add draws. That is a guess about the game.
- **Guest state blocks do not capture or apply.** `IDirect3DStateBlock9::Capture` and `Apply` have null function pointers (`rt/d3d9.c`), so `rt/com.c` returns success. The performance overlay uses a different block, created on the DXVK device (`CreateStateBlock` in `rt/hostd3d9.cpp`). Same question as queries: does the game call the guest methods?
- **Multisample is turned off on purpose, and the host would ignore it anyway.** `rt/firstrun.c` forces `iMultiSample=1` because "this port does not render" multisampling. Host render targets and depth surfaces are created with `D3DMULTISAMPLE_NONE`. What it would cost at 3840x2160, given that v18 measured draws and Present at a few milliseconds, is not measured. The GPU can be busy for other reasons. The overlay's GPU figure comes from DXVK's idle counter (`dxvk_fnv_stats`), and no session in the status notes quotes a GPU percentage for a busy outdoor scene.
- **Several device methods succeed and do no work.** `MultiplyTransform`, `GetFrontBufferData`, `SetCursorProperties`, `CreateAdditionalSwapChain`, `ProcessVertices`, `DrawRectPatch`, `DrawTriPatch` and the palette and N-patch methods are stubs or empty successes in `rt/d3d9.c`. `D3DXSaveTextureToFileA` returns success and writes nothing. The constant table and `D3DXCompileShader` are absent from `rt/d3dx.c`. The game reaches the Mojave with this set. Which of them a mod or an untested effect would call is the trace the near-term plan asks for.
- **Back-buffer format is forced.** `fill_pp` in `rt/hostd3d9.cpp` sets `D3DFMT_X8R8G8B8` whatever the game requested. No note says the game asked for something else.
- **The software rasterizer is still in the build.** `FNV_RENDERER=software`, or a failed DXVK `CreateDevice`, takes `rt/d3d9_swr.inc` (or `rt/hostd3d9_null.c` when DXVK is not linked). It draws triangles, interprets SM1–SM3 bytecode, and approximates fixed-function texturing at stage 0. It is the desktop fallback. It is not the PS5 path: `ps5/build.sh` always compiles `rt/hostd3d9.cpp`.
- **Dust and smoke with hard edges.** The status "To watch" line, after the v20 flicker fix. Cause unknown. See the near-term plan. No code comment names a remaining particle bug beyond the `D3DLOCK_DISCARD` note in `rt/hostd3d9.cpp`.
- **A movie the game draws into part of the screen.** `bk_BinkCopyToBufferRect` copies a rectangle of the frame into a locked texture. Its comment says the game tiles the movie into 256x256 textures. Those tiles came out black through DXVK, so `movie_overlay` in `rt/hostd3d9.cpp` draws the decoded frame over the whole screen, scaled to fit, whenever `bink_picture` reports a movie. The intro is that case (v15: `FNVIntro.bik`, skipped with a button). A movie meant to occupy part of the frame would be covered by that full-screen overlay for as long as it is the playing movie. No note says a second movie was tried. **Speculation:** a terminal or an in-world television is such a movie. The tree does not name one.

## Audio

- **Doppler and cones are stored, not heard.** `rt/dsound.c` keeps listener velocity, source velocity and `doppler`. `gains` uses distance, min/max distance, rolloff and a left/right pan from the listener basis. It does not read velocity. Cone methods are empty COM stubs. Whether the game sets a non-zero velocity on the buffers it plays is not in the notes. The base-game sound that is known to work is WAV, Ogg, MP3 and the intro's first Bink track (v13, v15).
- **Music that is not MP3 stays silent.** `gb_Render` in `rt/dshow.c` decodes with dr_mp3. Any other stream logs that music stays silent and returns success. The game's own music is described as MP3. A mod that ships another format would hit this.
- **Bink audio is the first track, from a path.** `bk_BinkOpen` refuses the open-by-handle flag and reads track 0 only. A movie with its useful audio on another track would play the wrong one, or none.
- **The mix is stereo software.** `ds_GetSpeakerConfig` reports stereo. The file header says there is no hardware voice, matching DirectSound on Vista and later. EAX and `SetFX` are empty. No note says the game asked for a hardware buffer and failed.
- **Sample rate is 48 kHz.** `plat_audio_open` asks SDL for 48000 Hz, stereo, S16. Buffers are resampled in the mix by stepping `freq / g_rate`. A device that opens at another rate would disagree with that assumption. The code logs an SDL failure and returns 0. What the PS5 AudioOut device actually grants is not written down.

## Input

- **On PS5 the intended device is the DualSense.** `plat_init` under `__PROSPERO__` initialises the game controller and events, not a video window (`rt/platform_sdl.c`). Settings removes "360 Controller" and "Mouse Sensitivity" (v28). Keyboard and mouse on that build depend on SDL delivering events with no window. Nothing in the notes says a USB keyboard was tried. Character creation is reached (v13). The notes do not say how the name was entered, so that session does not show whether a system keyboard works.
- **`GetAsyncKeyState` always returns 0.** `rt/user32.c`. DirectInput's `GetDeviceState` is the path that sees `plat_keys`. Any game code that polls the async API sees no keys. No note says the game uses it for gameplay. The console's text path, per the comment in `rt/user32.c`, is `WM_CHAR` from `plat_next_char`.
- **The DirectInput startup line is wrong on the Linux SDL build.** It always says the devices report no input. See the near-term plan.
- **PC adaptive triggers are not sent.** `plat_pad_triggers` outside `__PROSPERO__` is empty, with the comment "a PC's DualSense: not done". The desktop build is a development target. The player page does not promise trigger effects there.
- **Touchpad is a button.** The click is mapped to the game's Back (`rt/platform_sdl.c`, v33). Motion on the pad is not a cursor. The game's Wait prompt is that click. Whether a later UI wants the pad as a pointer is not raised by the current notes.
- **Haptics beyond rumble and the adaptive-trigger effect.** `XInputSetState` calls `plat_rumble` (`SDL_GameControllerRumble`). The shot "kick" is a change to the trigger effect while R2 is held (`rt/dualsense.c`). No call sets a DualSense vibration waveform apart from those. The roadmap's word "haptics" is not tied to a further API in this tree.

## Performance

- **Busy views are limited by the main thread, per draw.** v35. The open part is how that time splits between the recompiled game, `sync_state`, and DXVK pipeline compiles inside the draw (`hb_frame_end` in `rt/hostd3d9.cpp` puts compiles in the draw bucket). The near-term plan is to measure that, not to assume a fix.
- **Per-thread CPU clocks read 0 on PS5.** `perf_line` in `rt/main.c` skips them and keeps the process total from `getrusage`. The overlay's per-core row uses `kern.cp_times` (`rt/osd.c`). v35 says that sysctl is not available, and the row is omitted when the call fails. Whether some other PS5 counter can fill it is unknown. The player page used to claim the row unconditionally; it now matches this.
- **The idle-camera dip.** v35 attributes the long stand-still pattern to draw count on the vanity camera, with memory flat. **Speculation** in that note is the word "almost certainly". A second long session with the camera locked, if one is ever logged, would confirm it. It is not an open leak.
- **Shader compiles versus the game's own stalls.** v16 added compiler threads and the overlay counter because stutters were suspected compiles. v18's breakdown then put most long frames on game code, including bursts of hundreds of D3D objects created on one frame. Which of those still happen on a second visit to the same area is not logged. A disk shader cache is **speculation** until that measurement exists. Nothing sets `DXVK_STATE_CACHE` or a similar path.
- **Above 60 fps the engine's physics go wrong.** The comment in `rt/osd.c`. It names Havok's `fMaxTime` substep (1/60 s) and says a cap above 60 is refused for that reason. It does not name the functions that break, or whether `fMaxTime` alone is the fix. That is the long-term plan's first unknown.
- **Autosave write time.** v18: about 255 ms, of which about 150 ms was file writes, before v20 gathered writes into 256 KB pieces. No later session re-measures the save. Whether the gather brought the 255 ms down is not in the notes.

## Saves, mods, and the script extender

- **PC saves, both directions.** The player FAQ says the format is the PC format and that copying saves across has not been tested widely. No code converts a save. The open question is practical: a 1.4.0.525 save with a given set of add-ons, loaded here, and a save written here, loaded by the PC game. The near-term plan states the done criterion.
- **Where `plugins.txt` lives, and the exact text the game accepts.** The roadmap says the app should generate it. No file in this repository reads or writes that name. Guessing the path from the PC game, without a trace of the game opening it, would be an invention. `FNV_TRACE` on `CreateFileA` during a boot that has plugins is the way to settle it.
- **Archive invalidation is implemented for the assets overlay only.** `write_invalidation` in `rt/overlay.c` writes bare filenames into `Data/ArchiveInvalidation.txt` on the overlay it was given, and keeps the game's existing list when that file is not inside the overlay. v21 and v22 record that this was not enough for the button prompts, because the game draws those from `textures\interface\interfaceshared0.dds` rather than from the loose button files. A mod that replaces an atlas by loose files can hit the same rule. The fingerprint overwrite in `rt/glyphs.c` is specific to that atlas and to the Pip-Boy arm. It is not a general mod hook.
- **Load order, master files, and the add-on list.** The early menu note says the game loaded FalloutNV.esm and every DLC esm that was present. Nothing in the runtime builds that list. Turning a mod plugin on means getting the game to load it through whatever file it already reads. That file is the unknown above.
- **NVSE cannot arrive as a Windows DLL.** `k_LoadLibraryA` resolves only `g_mod_names` in `rt/kernel32.c`. The roadmap already says the extender is rebuilt in, via hooks. How many of xNVSE's patches fit the "keep this list short" comment on `HOOKS` is not inventoried. Closed-source plugins are out of scope for the reason the roadmap gives: there is nothing to rebuild.
- **Quitting skips the game's teardown.** `h_007D0BF0` runs the original Exit Game function and then `rt_exit`, which on PS5 is `sceSystemServiceLoadExec("exit")` (`rt/api.c`). The comment says the game's own teardown crashes, which is why the loading-screen hooks exist too (`rt/hooks.c`). **Speculation:** the skipped teardown would have flushed something the player can notice. The notes do not name such a loss. Settings are written through the game's INI calls at other times.

## Legal and assets

- **No game files are in the repository, and the app checks the executable.** `map_image` in `rt/main.c` requires the FNV-1a of `.text` to match the GOG 1.4.0.525 executable (`EXE_TEXT_FNV`). A data mismatch logs and continues. Steam's executable is described as encrypted on disk. The open legal point is distribution of the generated C, which is a translation of that executable and is not committed. The project licence (GPL-3.0-or-later, [LICENSE](../LICENSE)) covers this repository's source. [README.md](../README.md) states that it does not cover the game, and that game files must not be shared.
- **fnv_decomp's function list is used at build time and not relicensed.** [CREDITS.md](../CREDITS.md). Anyone packaging a build that was seeded from those addresses needs their own answer to that project's terms. This file cannot give one.
- **Button prompts and the icon are original drawings.** `tools/make_glyphs.py`, `tools/make_icon.py`, and the credits. They are not Sony assets and not game textures. The atlas overwrite (`rt/glyphs.c`) replaces cells inside a texture that comes from the player's install at runtime. The modified pixels are not stored as a copy of the game's atlas. The risk, if someone later commits a captured atlas "for testing", is shipping the game's texture. The tree does not contain one.
- **DejaVu is the lettering, under its own licence.** `LICENSES/Bitstream-Vera.txt`, rendered into `assets/internal/osd_font.a8` and into the shoulder-button labels. The font files themselves are not in the repository. The rendered bits are.
- **FFmpeg in the PS5 app is the GPL build.** [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md): PacBrew's 7.0.1 package, built with `--enable-gpl --enable-version3`. On PS5, `rt/bink.c` names `ff_bink_decoder`, `ff_binkaudio_dct_decoder` and `ff_binkaudio_rdft_decoder` directly. The comment says that avoids linking `allcodecs.o`, which would pull in every codec that library was built with, x264 included. The notices say the app can be relinked against another FFmpeg with `ps5/build.sh`. A replacement still has to provide those three decoders. The rest of that package's configure line is not copied into this repository.
- **Trophies, if they are added, pull in another GPL project and a platform service.** The roadmap names RecompTrophy. What the jailbreak allows an app to register as a trophy is not described here. A trophy list that copies the game's achievement text would be a separate asset question. No such list is in the tree.

## Platform

- **Guest memory on PS5 is direct memory, and running out exits.** `rt/mem.c`: the flexible budget is too small, so commits use `ps5_shm` in 64 KiB units. Failure prints "out of direct memory" and `exit(2)`. The perf line's "game RAM" is `g_guest_backed`, which is that pool. "Host memory free" is flexible memory, a different pool (331 MB free in the v15 and v16 notes, with game RAM around 1.0–1.1 GB). How close a full playthrough with every add-on gets to the console's direct-memory ceiling is not logged. The usable guest top is `0xEFFF0000` (`vm_top`), under the thunks at `0xF0000000`.
- **The 4 GiB window has to be reservable.** On Linux that is an anonymous `mmap` of 4 GiB with `PROT_NONE`. On PS5 it is `ps5_vrange_reserve`. A host that cannot reserve a contiguous 4 GiB range cannot run the generated code, because guest addresses are a single add from `g_guest_mem` (`rt/x86.h`). The old "Next" list said this, and the PS5 path now does reserve it. Other 64-bit hosts are untested.
- **Networking is refused.** `rt/misc.c` marks WSOCK32 with the comment "networking is not available": `socket` returns `0xffffffff`, `gethostbyname` returns null. GOG Galaxy's wrapper reports that it is not running. The sessions in the status notes do not mention a socket call. **Speculation:** a mod, or a path the played sessions never took, would hit this and then fail on its own.
- **The process is killed on fatal errors.** `rt_fatal` prints the guest stack and `_exit(3)`. On a guest fault the address is translated back when it falls inside the window (`rt/main.c`). There is no crash dialog and no save of the crashing state. That matches a homebrew app. It is a poor bug report if the player does not still have `fnv.log`.
- **Per-core load, temperatures, and the pad library are direct imports because runtime lookup failed.** v28 and v33: `scePadSetTriggerEffect`, `scePadResetLightBar`, `sceKernelGetCpuTemperature`, `sceKernelGetSocSensorTemperature`. A firmware where those symbols are absent will fail at link or at the call. The temperature path logs "refused" and leaves the reading out. The pad path has no such softness if the import itself is missing at load.
- **One global DXVK device for the overlay stats.** `dxvk_fnv_stats` reads `g_fnvDevice`, set from the `DxvkDevice` constructor in the patch. A second device would make the counters follow the latest one. The game creates one device. **Speculation:** a second device, if some future path made one, would report the wrong idle time.
- **The app id is `PPSA97701`.** `ps5/sce_sys/param.json` and `ps5/build.sh`. What that title id collides with, on a console that already has an app under the same id, is a packaging question. The install instructions say to copy the folder to `/data/homebrew/PPSA97701` and to overwrite it on update, keeping `game/` and `user/`.
